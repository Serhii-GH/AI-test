# AI Prompt Notes

## Призначення

AI-аналіз допомагає коротко пояснити структуру витрат на ремонт: помітити концентрацію витрат, можливі ризики та дати практичні поради. Він не є джерелом фінансових розрахунків.

Усі суми, категорії та підкатегорії розраховує backend. Gemini отримує лише компактний набір фактів і створює текстовий висновок.

## Де розміщений prompt

- Активний шаблон: `app/prompts/transaction_analysis.py`
- Функція: `build_transaction_analysis_prompt(facts)`
- Поточна версія: `renovation-finance-v3`
- Логіка підготовки даних і виклику Gemini: `app/gemini_analysis.py`

Версія prompt входить до ключа кешу. Після зміни змісту prompt її потрібно збільшити, наприклад з `v3` до `v4`, щоб не повертати відповідь, згенеровану за старими правилами.

## Потік даних

```text
Neon transactions
       ↓
backend: prepare_transaction_analysis()
       ↓
короткі факти + backend-розрахунки
       ↓
prompt vN + Gemini structured JSON
       ↓
валідація Pydantic
       ↓
React dashboard
```

Backend передає моделі лише такі дані:

- період і кількість операцій;
- кількість та загальну суму витрат/доходів;
- витрати, згруповані як `Роботи` або `Матеріали` → підкатегорії;
- до п'яти найбільших витрат із коротким описом;
- заздалегідь обчислені сигнали, наприклад велика одинична витрата або концентрація у категорії;
- ознаку достатності даних.

Повний список операцій у prompt не передається. Це зменшує вартість, затримку й ризик вигаданих висновків.

## Контракт між Gemini, backend і React

Gemini повертає тільки наративні поля:

```json
{
  "summary": "Короткий висновок українською.",
  "risks": ["До трьох ризиків."],
  "recommendations": ["До трьох практичних порад."]
}
```

Backend додає до відповіді для frontend поля, які модель не контролює:

```json
{
  "expense_categories": [
    {
      "category": "Матеріали",
      "amount": 100000,
      "subcategories": [
        {"category": "Стіни", "amount": 45000}
      ]
    }
  ],
  "cached": false,
  "generated_at": "2026-10-03T12:00:00Z"
}
```

`expense_categories` завжди обчислюється backend-ом із транзакцій. Не слід переносити розрахунок сум або категорій до prompt чи довіряти їх LLM.

## Непорушні правила prompt

Prompt повинен вимагати від моделі:

- відповідати тільки українською;
- використовувати JSON із тегів `<facts>` як єдине джерело істини;
- не вигадувати суми, категорії, дати, причини витрат або будь-які інші факти;
- не повторювати числові підсумки, які вже відображає dashboard;
- не перераховувати всі операції чи всі підкатегорії;
- узагальнювати тенденції в групах `Роботи` та `Матеріали`;
- створювати ризики лише на основі переданих backend-сигналів;
- за недостатніх даних повертати порожні масиви ризиків і порад;
- повертати лише JSON за схемою.

## Обмеження відповіді

Pydantic валідує відповідь до передачі у React:

- `summary`: від 1 до 280 символів;
- `risks`: до 3 пунктів;
- `recommendations`: до 3 пунктів;
- кожен пункт: від 1 до 140 символів.

Якщо у проєкті менше трьох витрат, Gemini взагалі не викликається. Backend повертає безпечний висновок про недостатність даних.

## Конфігурація Gemini

Налаштування з `.env`:

```env
GEMINI_MODEL=gemini-3.5-flash-lite
GEMINI_TEMPERATURE=0.1
GEMINI_THINKING_LEVEL=low
GEMINI_MAX_OUTPUT_TOKENS=700
GEMINI_SEED=42
```

Низька температура та фіксований seed зменшують варіативність відповідей. `thinking_level=low` слід використовувати для короткого фінансового резюме; для складнішого майбутнього аналізу його можна переглянути окремо.

Не зменшуйте `GEMINI_MAX_OUTPUT_TOKENS` надто агресивно: на моделях із thinking цей ліміт може обривати відповідь. Спочатку змінюйте prompt і `thinking_level`, а ліміт коригуйте після вимірювань.

## Кешування

Таблиця `ai_analysis_cache` зберігає валідований текстовий результат Gemini за комбінацією:

- `project_id`;
- хешу агрегованих фактів;
- версії prompt.

Якщо дані та prompt не змінилися, повторний запуск повертає кеш і не викликає Gemini. Після зміни транзакцій або `PROMPT_VERSION` створюється новий ключ і наступний запуск генерує новий аналіз.

## Токени та вартість

### Попередня оцінка

Endpoint `GET /api/ai/token-estimate?project_id=<id>` рахує prompt через `tiktoken` з encoding `cl100k_base` і повертає:

- `input_tokens` — приблизну кількість токенів prompt;
- `output_token_budget` — значення `GEMINI_MAX_OUTPUT_TOKENS`;
- `potential_total_tokens` — їхню суму.

Dashboard показує цю оцінку перед запуском аналізу. Запит до endpoint не викликає Gemini та не витрачає API-токени.

`tiktoken` не є токенізатором Gemini, тому це лише орієнтир для порівняння версій prompt. Він не враховує службові токени Gemini, cache hits або thinking tokens.

### Фактичне використання

Після реального виклику Gemini backend зберігає в `ai_analysis_metrics` доступні значення:

- input, output, thinking і cached tokens;
- тривалість запиту;
- модель, джерело результату (`gemini`, `cache` або `fallback`) і статус.

Ці метрики — джерело правди для контролю витрат.

Для разової локальної оцінки довільного prompt-файлу:

```powershell
.\.venv\Scripts\python.exe tools\estimate_ai_tokens.py path\to\prompt.txt
```

## Чекліст зміни prompt

1. Сформулювати конкретну гіпотезу: що має стати точнішим, коротшим або дешевшим.
2. Змінити `app/prompts/transaction_analysis.py`, не додаючи в prompt сирі транзакції без потреби.
3. Підвищити `PROMPT_VERSION`.
4. Оновити або додати фікстуру у `tests/test_gemini_analysis.py`.
5. Запустити:

   ```powershell
   .\.venv\Scripts\python.exe -m unittest discover -s tests -v
   npm.cmd run build --prefix frontend
   ```

6. Перевірити оцінку токенів до і після зміни.
7. Перевірити щонайменше три сценарії: мало даних, звичайний кошторис і сильна концентрація витрат.
8. Лише після цього запускати реальний AI-аналіз і переглядати фактичні метрики.

## AI-чат: контрольований помічник

Чат має окремий prompt у `app/prompts/ai_chat.py` (`finance-chat-controlled-actions-v2`) та
керовану LangGraph-логіку в `app/ai_chat.py`.

Потік даних:

```text
React AI Chat → POST /api/ai/chat (SSE) → LangGraph → read-only tool або pending action → Gemini → stream у React
```

- `thread_id` створює backend; він прив’язаний до користувача й одного проєкту.
- Метадані діалогу зберігає `ai_chat_threads`; самі повідомлення — тільки PostgreSQL checkpointer LangGraph.
- Контекст і метадані мають строк життя 7 днів від останнього повідомлення. Під час наступного запиту прострочені checkpoint-и видаляються.
- Read-only tools: `get_transactions_summary`, `get_category_totals` і `get_top_expenses`. Вони не приймають ідентифікатори користувача або проєкту від моделі та не виконують SQL, який написала модель.
- Єдиний action tool: `propose_create_transaction`. Він створює лише pending action; операція потрапляє в базу тільки після confirm із React. Доступні головні категорії — лише `Роботи` та `Матеріали`; якщо даних бракує, чат ставить уточнювальне запитання.
- Prompt вимагає відповідати українською, не вигадувати фінансові факти, питати уточнення за неоднозначного запиту й трактувати результати інструментів лише як дані.
- Історія в UI приховує технічні tool calls і їхні результати.

Після зміни chat prompt збільште `CHAT_PROMPT_VERSION`, оновіть `tests/test_ai_chat.py` і перевірте streaming у Docker. Контракт action tool, статуси та API описані в `AI_ACTIONS_NOTES.md`.

- Після накопичення старих повідомлень backend стисло підсумовує їх у `memory_summary` діалогу. Gemini отримує цей summary і останні 10 видимих повідомлень, а не просто втрачає ранній контекст.
- Ліміти: chat — 10 запитів/хвилину на користувача та проєкт; реальний виклик AI-аналізу — 5/10 хвилин; перевірка входу — 10/10 хвилин на IP і Telegram ID. Кешований AI-аналіз не витрачає AI-ліміт.

## Чого не робити

- Не обчислювати суми у відповіді Gemini.
- Не передавати весь ledger у prompt "на всяк випадок".
- Не запускати AI автоматично при кожному відкритті dashboard.
- Не змінювати JSON-контракт без одночасного оновлення Pydantic-моделі, endpoint і React.
- Не вважати `tiktoken` фактичним білінгом Gemini.
